HEAVY CODING

AI 不是故意说谎 —— 它会幻觉出成功。
这套工作流让每个结论都交一笔过路费：退出码，否则什么都不算。

v1.0.0-beta.1 · 首次公开测试版 MIT Bash + Python · 零第三方依赖 十四道门 github.com/PoorThoth/heavy-coding

问题不在能力，在验收

AI 报「做完了」，用的是产出这个 bug 的同一个上下文。要求它诚实的提示词、同一个模型的自审、跑错测试的绿 CI —— 失败原因都是同一个：判官就是被告。只要判官换成一个机器可验的事实，循环里就没有任何一步能「既错了又通过」。

这是什么

把一次编程会话包进 14 个检查点。每个检查点只能被机器能验的东西放行：真执行过的用例、真跑过的 diff 行、真的存在的 file:line。执行器的散文从来不算证据 —— 只有产物上的 rc=0 算。

05 为什么站得住 —— 以及造它花了什么

五条不肯破的设计铁律

  1. 自述不算数。执行器的输出，只有在某条命令对某个机器可验的产物返回 rc=0 时才成为证据。「已验证」「应该没问题」「看着挺好」都不是结果。
  2. 红基线是数据，不是失败。真实仓库一打开就是红的。把红集合记一次，之后只对新增的失败发红 —— 会喊狼来了的门，一周内就没人看。
  3. 豁免必须显式且进版本库。测不了的文件写进 .diffcovignore 并写理由，在 diff 里看得见。阈值绝不偷偷下调。
  4. 管门禁的门禁要在沙盒里验。检查器不能自证：注入一个已知失败，看它红；修好，看它绿。
  5. 度量范围圈到本票。git diff HEAD 会带上别人未提交的活儿，量出来的数字毫无意义。
