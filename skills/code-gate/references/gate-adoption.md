# 门禁为什么会「存在但没人用」——诊断与修法

写这套入口机制之前，先确认不是又在写一份没人加载的规范。下面顺序按「先量、后改」排。

## 1. 先量化，别凭感觉归因

判断某套流程是否真在运行，用**使用痕迹**而不是**文件是否存在**：

| 想知道的 | 怎么量 | 判据 |
|---|---|---|
| 技能有没有被加载 | 在会话库里搜 `skill_view(<技能名>)` 的命中条数与会话数 | 全期有、近一月 0 ⇒ 从没进过选择环节 |
| 代码活有没有停 | 搜 `git commit` / `pytest` / `go test` 的命中 | 活没停而门禁 0 次 ⇒ 是绕开，不是没活 |
| 门禁跑过几票 | 账本的 `cmd=deleg` 记录，按 `dir` 分组 | 全在沙盒目录、真项目 0 票 ⇒ 脚手架没搬过去 |
| 有没有强制点 | `hooks/` 是否为空、仓库有没有 pre-commit | 空 ⇒ 规则只能靠自觉 |

常见误判：把「技能太多导致混淆」当第一因。先数一遍**与任务同类的技能有几条描述**——通常十几条里真正相关的不到一成，失败形态是「任何相关技能都没加载」，不是「加载了错的」。混淆会选错，不会完全不选。

## 2. 四个真因（按权重）

1. **规则住错地方**：执行率取决于规则在不在每轮必注入的文件（`AGENTS.md` / memory），不取决于规则本身多正确。同一份「改完必须跑测试」写进项目 `AGENTS.md` 会被执行，写进 600 行技能里不会——这是可以拿两个仓库对照验证的事实。
2. **入口成本 > 收益，且前置不存在**：几百行的规范加载即上万 token；若真实仓库里连任务骨架目录都没有，即使加载了也要现搭脚手架，理性选择就是绕开。
3. **前置会静默失效**：缺凭据时工具报「没 key」却 `rc=0`、零产出，这种失败形态最伤人——遇到一次，以后就不选这条路。
4. **没有强制点、没有巡检**：命令行工具只在有人主动敲时存在；账本停更一个月没人发现，等于「门禁代替信任」退化成「文档代替纪律」。

## 3. 修法（按性价比）

| 动作 | 治哪个 | 写法 |
|---|---|---|
| 锚点进 always-on | 1 | 在 `AGENTS.md` 加一段带 START/END 标记的短条款（触发/两种模式/只认退出码/收尾报三件），memory 放一行指针 |
| 瘦入口 | 2 | 新建 ≤80 行 runbook（判模式 → 命令 → 退出码表 → 静默失效前置）；把几百行那份标成「参考文档」并写「日常跑的不是本文件」 |
| 消灭静默失效 | 3 | 凭据读不到就自动从本机 `.env` 读，**只报长度与来源，绝不打印值**；缺什么就打印修复路径 |
| 守门 + 巡检 | 4 | 零 token 脚本巡检「窗口内没用过」「入口被改没」，空输出=不投递（见 `cron-report-formatting` 的纯告警型看门狗条目） |

## 4. 反模式

- **只写规范不改存放位置**：规范越全越没人读；完整度不是执行率。
- **把入口做成一份 600 行的文档**：加载成本高到足以让「直接干」成为理性选择。
- **两套口径并存**（图上写一套、技能里一套、退出码又是一套）：执行时按哪套都能争，最后按「省事的那套」。
- **报警阈值按历史陈旧度**：第一次跑就为旧账报警，用户会关掉巡检，之后真出事也没人知道。
